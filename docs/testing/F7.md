# F7 test steps: message thread per request

Feature: every rental request has its own message thread. The seeker and the ad's landlord side (the poster and the building's caretakers) write to each other on the request's page, `/dashboard/requests/<id>`. New messages and "Seen" marks arrive live (Supabase Realtime), and unread counts show in the menu (**Messages**), on the dashboard, on request cards and in the requests inbox. A new **Messages** page lists every conversation. Nobody else can read a thread, admins included.
Rules: messages can be written while a request is new, shortlisted (and, from F8, offered or confirmed); a declined, withdrawn or expired request is read-only. Messages pause while the ad is hidden or rejected. Suspended members cannot write, and the landlord cannot write to a suspended member. Until the landlord answers (writes or shortlists), the seeker can add at most 3 messages. At most 30 messages per member in 10 minutes. Messages are 1 to 1000 characters.
Done when (FR25): M1 and N write to each other on one request, each sees the other's message appear without reloading, the unread number goes up in the other person's menu and back to zero when they open the thread, and the thread becomes read-only after the request is declined.

## Before you start
- Run the F7 migration on the dev project once, in Supabase **SQL Editor**: `supabase/migrations/20261031120000_f7_messages.sql`. Running it twice is safe. It also turns on live updates for the new `messages` table.
- Check that it ran: the query below shows one row where every column is `true`.

```sql
-- Query 0: is the F7 migration applied?
select
  to_regclass('public.messages') is not null                                   as messages,
  exists (select 1 from pg_proc where proname = 'send_message'
            and pronamespace = 'public'::regnamespace)                         as send_message,
  exists (select 1 from pg_proc where proname = 'message_threads'
            and pronamespace = 'public'::regnamespace)                         as message_threads,
  exists (select 1 from pg_publication_tables
            where pubname = 'supabase_realtime' and tablename = 'messages')    as live_updates,
  exists (select 1 from pg_policies where tablename = 'messages')              as read_policy;
```
- Where to run SQL: Supabase dashboard, organization House Manager, project house-manager-dev, **SQL Editor**, **New query**, paste, **Run**. Use a new query tab for each one.
- Test on the PR preview (https://house-manager-git-feat-f7-messages-sifat14.vercel.app), not the live site, which still runs main.

## 10. Privacy (Supabase SQL Editor)
Each query pretends to be someone for a moment. Run each one on its own.

```sql
-- Query 1: a visitor cannot read or send messages (expect: false, false)
select
  has_table_privilege('anon', 'public.messages', 'select')                    as can_read,
  has_function_privilege('anon', 'public.send_message(uuid, text)', 'execute') as can_send;
```

```sql
-- Query 2: an admin reads no messages and has no conversations (expect: 0, 0)
select set_config('request.jwt.claims', json_build_object('sub', id, 'role', 'authenticated')::text, true)
from auth.users where email = 'housemanagerbd+admin1@gmail.com';
set local role authenticated;
select
  (select count(*) from public.messages)          as messages_seen,
  (select count(*) from public.message_threads()) as conversations;
```

```sql
-- Query 3: M2 reads only messages on M2's own requests (expect: 0)
select set_config('request.jwt.claims', json_build_object('sub', id, 'role', 'authenticated')::text, true)
from auth.users where email = 'housemanagerbd+m2@gmail.com';
set local role authenticated;
select count(*) as other_peoples_messages
from public.messages
where request_id not in (select id from public.rental_requests where tenant_id = auth.uid());
```

```sql
-- Query 4: nobody writes the table directly, not even a member of the thread
-- (expect: ERROR: permission denied for table messages)
select set_config('request.jwt.claims', json_build_object('sub', id, 'role', 'authenticated')::text, true)
from auth.users where email = 'housemanagerbd+m1@gmail.com';
set local role authenticated;
insert into public.messages (request_id, sender_id, body)
select id, auth.uid(), 'test' from public.rental_requests where tenant_id = auth.uid() limit 1;
```

```sql
-- Query 5: what landlord N sees: every thread on N's ads, with unread counts
select set_config('request.jwt.claims', json_build_object('sub', id, 'role', 'authenticated')::text, true)
from auth.users where email = 'housemanagerbd+n@gmail.com';
set local role authenticated;
select my_side, other_name, listing_title, request_status, last_body, unread_count
from public.message_threads();
```

## 11. Clean up
```sql
-- Query 6: delete the test accounts' requests (their messages go with them)
-- and everything they posted (ads, drafts, units, buildings), then reset N.
-- Other accounts are not touched.
delete from public.rental_requests
where tenant_id in (select id from auth.users where email like 'housemanagerbd+%@gmail.com');
delete from public.listings
where posted_by in (select id from auth.users where email like 'housemanagerbd+%@gmail.com');
delete from public.units
where building_id in (select id from public.buildings
  where created_by in (select id from auth.users where email like 'housemanagerbd+%@gmail.com'));
delete from public.buildings
where created_by in (select id from auth.users where email like 'housemanagerbd+%@gmail.com');
update public.profiles set trust_level = 0, is_banned = false
where id in (select id from auth.users where email like 'housemanagerbd+%@gmail.com' and email not like 'housemanagerbd+admin%');
```
The test accounts stay for the next feature (F8 uses the same requests and threads). The photo files stay in N's folder in `listing-photos`; delete them there if you like.
