# F12 test steps: SEO, speed, accessibility and the end-to-end tests

Feature: the last TO-LET feature polishes what is already there. No database change.
- **SEO**: `robots.txt` and `sitemap.xml` (home, search, the indexable area, thana and ad type pages, every live ad, rights, terms and privacy, each in both languages with hreflang links). Structured data (JSON-LD) on ad pages (the listing with rent, rooms, size and area, never the street address or phone), breadcrumbs on ad and area pages, and the site name and search box on the home page. Every public page sets its own canonical link; before F12, pages without one (sign-up, for example) pointed to the home page. A site icon (browser tab, phone home screen) and a share picture in each language for pages without a photo.
- **New pages**: **Know your rights** (`/rights`, the Premises Rent Control Act 1991 in plain words), **Terms of use** (`/terms`) and **Privacy policy** (`/privacy`), in both languages, linked from the footer of every page; the sign-up form links to the terms and the privacy policy.
- **Speed**: public pages download about 155 KB less JavaScript (the validation library and the Supabase client no longer load for visitors), the Bangla font is preloaded so text no longer jumps when it arrives, and the browser connects to Supabase Storage early for photos.
- **Accessibility**: a "Skip to main content" link (first Tab on every page), every page has one main heading, the language button and the account menu have names that match what they show, links inside text are underlined, the search results have a heading for screen readers, and the message list is announced correctly.
- **End-to-end tests** (Playwright, in `e2e/`): the public pages in both languages with an accessibility check, and the whole story from a new ad to a confirmed tenancy.
- **Keep-alive**: a GitHub Actions workflow that keeps the free Supabase project from pausing.

Done when (FR33 and the F12 line of the plan): the sitemap lists the live ads and the public pages, ads have structured data and share previews, Lighthouse shows 100 for accessibility and SEO on the public pages of the live site, axe finds no serious problems, the keep-alive workflow runs, and the Playwright test goes from a new ad to a tenancy.

## 7. End-to-end tests (a laptop)
The tests are in `e2e/`. They drive Chrome like a person would, against a site that is already running.

Once per laptop, in the repo folder (Node 24, the branch checked out):
```
npm install
npx playwright install chromium
```

### 7.1 Public pages (read-only, safe anywhere)
PowerShell on Windows:
```
$env:E2E_BASE_URL="https://house-manager-git-feat-f12-polish-sifat14.vercel.app"; npm run test:e2e:public
```
(macOS or Linux: `E2E_BASE_URL=https://... npm run test:e2e:public`.)

Expected: `24 passed`. It opens home, search, an area page, rights, terms, privacy, sign-up, login and password reset in both languages, an ad page, a page that does not exist, `robots.txt` and `sitemap.xml`, and checks the skip link. On each page it runs axe (WCAG 2.1 AA) and fails on any serious problem. A report with screenshots of failures is in `e2e-report/index.html`.

### 7.2 From a new ad to a tenancy (writes test data)
It logs in as N, M1 and (only if the new ad waits for review) ADM, with their passwords:
```
$env:E2E_BASE_URL="https://house-manager-git-feat-f12-polish-sifat14.vercel.app"; $env:E2E_PASSWORD="<the test accounts' password>"; npx playwright test e2e/request-to-tenancy.spec.ts
```
If the accounts have different passwords, set `E2E_LANDLORD_PASSWORD`, `E2E_SEEKER_PASSWORD` and `E2E_ADMIN_PASSWORD` instead. Other accounts: `E2E_LANDLORD_EMAIL`, `E2E_SEEKER_EMAIL`, `E2E_ADMIN_EMAIL`. Never write a password into a file in the repo.

N needs a mobile number on **Profile** (it becomes the ad's contact number) and M1 a name and a mobile number. M1 must not have an open request on more than 9 ads.

Expected: `1 passed` in about a minute. What it does, in order: N adds a building `E2E <code> House` in Mirpur 10 and a flat `2A`, posts `E2E <code> two bedroom flat for a family` (Family, 18,000 taka, 1 month advance) with 4 new pictures; if the ad waits for review, ADM approves it. M1 sends a request. N shortlists it and writes a message; N adds visit times for tomorrow 10 to 11 am and M1 books the 10:00 visit; N makes an offer; M1 accepts with an NID number, a photo and an address; both see the tenancy, and the ad is rented. Emails go to the project Gmail as usual.

Then check it with Query 1 and clean up with Query 2.

```sql
-- Query 1: what the end-to-end test made (newest first)
select l.title, l.status, r.status as request_status,
       (select count(*) from public.tenancies t where t.listing_id = l.id) as tenancies
from public.listings l
left join public.rental_requests r on r.listing_id = l.id
where l.title like 'E2E %'
order by l.created_at desc;
```
Expected: the newest row `rented`, `confirmed`, `1`.
